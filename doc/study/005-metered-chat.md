# Metered Chat Study

## Request

Let an authenticated user select an active catalog model, send a prompt, receive and store a reply, and charge credits based on input/output token usage and that model's catalog rates. Use a clearly labeled no-network MOCK backend only when no applicable proxy URL is configured; otherwise use the REAL proxy backend and the provider key selected by provider. A configured proxy failure is an error, never a reason to fall back to MOCK. Keep proxy URLs and request style configurable because the proxy contract is not yet known. Do not add streaming, uploads, web search, or full conversation-management features.

## Feasibility

The app already has active `CatalogModel` rows with separate provider `model_id` and integer input/output prices, an authenticated user model, a wallet ledger with an atomic non-negative debit service, and SQLite migrations. This supports a minimal synchronous chat page and per-exchange persistence without new dependencies. The provider protocol cannot be completely validated until the proxy's endpoint and request/response contract are supplied; the MOCK path and all metering logic can be tested without network access.

## Proposed Approach

- Add a provider-neutral interface that accepts the selected `CatalogModel`, prompt, and output-token limit and returns reply text plus optional input/output token counts. Implement interchangeable `MockBackend` and `ProxyBackend` implementations, with small provider/style adapters that normalize responses to the common result.
- Resolve the selected provider's endpoint from `LLM_PROXY_BASE_URL`, overridden by an optional `OPENAI_PROXY_BASE_URL`, `ANTHROPIC_PROXY_BASE_URL`, or `GOOGLE_PROXY_BASE_URL`. Use MOCK only when no applicable proxy URL is configured, regardless of whether an API key happens to be present. If an endpoint is configured but the provider key or request style is missing, return a sanitized configuration error instead of falling back. Select request serialization with `LLM_PROXY_REQUEST_STYLE` (`openai_compatible` or `provider_native`). Keep all addresses in environment settings; do not embed URL literals or provider endpoints in code.
- Treat configured REAL request failures as failures: return a clear sanitized message, create no exchange, and charge no credits. Do not silently turn an unreachable or rejected REAL request into a mock reply, which could conceal a proxy outage. If provider usage counts are absent, estimate input and output counts from their respective text lengths and record that estimates were used.
- Make MOCK mode deterministic and network-free. Return a visibly labeled simulated reply with estimated token counts, persist it like a successful exchange, and meter it using the same catalog rates so the demo exercises the complete billing path. Store an explicit mode/estimated-usage marker so MOCK replies are distinguishable from provider replies.
- Add a login-required chat page whose POST includes an active catalog-model ID and prompt. Re-fetch the model server-side and reject inactive or unknown selections; never accept prices or provider IDs from the client. Keep each prompt/reply as an independent exchange initially; do not add a conversation sidebar, rename/delete flows, or persisted model preference.
- Add a `ChatExchange` record containing user, catalog model, prompt, reply, input/output token counts, credits charged, timestamp, and mode/estimation metadata. Add an optional exchange foreign key to `WalletTransaction` for non-usage rows and require it for usage rows, so each negative usage ledger entry is traceable to its exchange. Preserve non-usage signup/top-up entries without an exchange.
- Calculate actual charge with integer arithmetic and round up once: `ceil((input_tokens * input_rate + output_tokens * output_rate) / 1000)`. Display the charge beside each stored reply. If token usage is missing, use the text-length estimates for that calculation.
- Before calling a backend, estimate prompt usage and include the configured maximum output tokens (suggested `LLM_MAX_OUTPUT_TOKENS`, default 512) in a conservative affordability pre-check. Do not reserve or debit credits before a successful reply. If the pre-check fails, show a clear insufficient-credit message and make no backend call. After a successful reply, calculate actual/estimated cost and, in one database transaction, create the exchange and call the existing atomic wallet service for a negative `usage` transaction linked to it. If the final debit fails because the balance changed after pre-check, roll back the exchange, discard the reply, charge nothing, and show a clear retry message.
- Add focused tests around the backend interface with no proxy configured and outbound HTTP patched/blocked. Cover model selection/active filtering, no-network mock replies, preflight insufficient balance, configured proxy errors with no exchange/debit or mock fallback, response usage parsing and text-length fallbacks, charge rounding, successful exchange/ledger linkage, final-debit failure and discarded reply, and balance non-negativity. Test credential redaction using only a synthetic sentinel (never a real credential): assert it appears neither in captured logs nor rendered errors. Never print or log request headers/credentials, and sanitize provider exceptions before display.
- Update README and `doc/wiki/` with MOCK/REAL configuration variable names, the provisional IDs requirement, per-exchange metering, the no-reservation concurrency limitation, and the fact that real wire formats cannot be confirmed until proxy details are provided. Blank/comment proxy URLs and key values in `.env.example` so a fresh clone selects MOCK without an external URL or key.

## Tradeoffs and Risks

- By decision, there is no credit reservation. A preflight check alone does not reserve funds: concurrent requests could both pass and both call the provider. The existing conditional wallet debit remains authoritative and prevents a negative balance; if the final debit fails after a successful provider reply, roll back the exchange, discard the reply, charge nothing, and tell the user to retry. The external provider may still have incurred cost for that discarded reply; document this limitation in the wiki.
- The output-token cap bounds the preflight estimate, but a text-length input estimate is heuristic and provider-reported usage can be larger. The final guarded debit remains authoritative. If actual cost exceeds available credits after a provider call, fail safely without a negative balance and follow the no-charge retry behavior above.
- Integer catalog prices require rounding partial-credit usage upward. The proposed combined ceiling avoids separately rounding input and output, but small exchanges may cost one whole credit even when their raw combined rate is below one.
- MOCK success should be metered from estimates to exercise wallet behavior, while provider/configuration errors should not be treated as successful MOCK replies. Mode and estimated-usage indicators make that distinction visible and auditable.
- The proxy's endpoint shape, headers, and response formats are unknown. Configuration can select the proxy endpoint and serialization style, but REAL integration needs the proxy contract before exact request/response compatibility can be established. No real network/key tests should be required for the feature suite.
- Prompt and reply text will be stored in SQLite. This is necessary for showing prior exchanges, but it is persistent user content; avoid logging it and keep this first version local as scoped.

## Configuration To Confirm During Planning

- The proxy's request/response contract for both configured request styles, including whether configured base URLs identify a full endpoint or a root URL.
- Whether the proxy requires any provider-specific paths or headers beyond the selected request style; do not guess these details or hardcode proxy addresses.

## Out of Scope

No streaming, upload handling, web search, provider SDK dependency, real endpoint/URL literals, real API keys in source/tests/docs/logs, chat session sidebar, session renaming/deleting, or charges for failed provider calls are proposed. A synthetic sentinel may be used in redaction tests, but never an actual credential.
