# Metered Chat

- `/chat/` is available to logged-in users. Each POST must select an active catalog model; its provider-specific provisional `model_id` is sent to the backend. Each prompt/reply is stored as an independent `ChatExchange` within a `Conversation`, retaining its own model and cost.
- The provider-neutral completion interface selects MOCK only when neither the shared nor selected-provider proxy endpoint is configured. MOCK makes no network request, returns a visibly labeled simulated reply, estimates token counts from text length, and charges credits using the same path as a successful REAL reply.
- REAL mode requires a configured endpoint, that provider's environment credential, and `LLM_PROXY_REQUEST_STYLE`. Provider-specific endpoint overrides take precedence over the shared endpoint. OpenAI-compatible and provider-native adapters normalize response text and usage. The exact proxy wire contract is not confirmed, so REAL compatibility must be validated when proxy details are supplied.
- A configured proxy/key/style error or failed request is shown as a sanitized error; the application never falls back to MOCK in that case. No exchange or usage transaction is written for failed calls. Credential values, headers, raw exception details, and proxy endpoint values must not be logged or shown.
- Use provider-reported input/output token counts when available; otherwise record text-length estimates and mark which counts are estimated. Charge is the combined input/output catalog rate rounded up once to whole credits per exchange.
- The chat form previews a conservative estimated maximum cost as the prompt and active model change. Its server endpoint and the submit-time affordability pre-check share the same `estimate_request_cost()` helper, which estimates the current prompt and includes the configured output-token allowance. The estimate endpoint is read-only and never calls a backend or changes the wallet. The current provider request does not send prior conversation history.
- The preview warns when its estimate exceeds the current balance. It is informational and may become stale; final pre-check and the atomic post-reply debit remain authoritative, and actual usage can produce a different final charge.
- Before backend invocation, the app checks wallet balance against estimated prompt use plus the configured maximum output allowance. It does not reserve credits. On successful replies, the exchange and linked negative `usage` ledger transaction commit atomically through the wallet service.
- If another request changes the balance after pre-check and the final debit is rejected, the exchange and reply are discarded with no charge and the user is asked to retry. The proxy may still have incurred cost for this discarded response; this is the accepted no-reservation concurrency limitation.
- Tests use MOCK mode with network calls blocked. REAL request formatting/parsing is tested with mocked responses; no provider credentials or endpoint values are required.
- Streaming, uploads, web search, and conversation sharing are not implemented.
